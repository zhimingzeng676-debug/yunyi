## 路线选择

1. 推荐：按边界拆规格，先串行完成纵向闭环。基础状态与持久化 → 安全执行与恢复 → Harness/MCP 集成及规划。先约定共享契约，完整写 requirements、design、tasks，再进入实现。优点是风险能逐项验证，便于后续独立实施；代价是需要维护跨规格追踪。
2. 单一大规格：所有模块放进同一份 requirements/design/tasks。前期文件少，但任务和审查范围大，后续并发容易共享边界冲突。
3. 从全功能 Harness 透明拦截开始：先解决真实客户端网络调用控制，再搭其余组件。直接验证关键价值，但受客户端接口影响最大，最小闭环启动较慢。

## 待验证的 spike 与通过条件

1. 工具链：验证 Python 3.11+ conda 环境、SDK 安装导入、CLI 启动、MCP stdio 握手；验证 agentic-tdd 对 pytest 的命令支持，用一次有明确断言失败原因的 RED 和相应 GREEN 检验验证器，保留退出码及日志。试验代码与产品实现分开。
2. Windows Harness 控制：fake harness 持续创建子进程和本地请求；实测暂停、恢复、退出清理、在途请求及文件写入边界。进程暂停不得表述为已实现可靠 API 拦截；Claude/Codex 能力分别验证。
3. 持久化与恢复：验证 SQLite 多进程争用、任务领取与崩溃恢复；已运行但结果未落盘的步骤必须进入待核对状态，不能盲目重放。
4. 执行与回滚：验证 argv 命令规则、路径边界、子进程超时清理以及已有脏文件的精确恢复；禁止以整仓 checkout/stash 作为默认回滚实现。

## 最小闭环验收提案

使用 fake harness 和可控本地网络探针：稳定 → 断网 → 执行一条已保存且获准的离线任务 → 写入结果及检查点 → 恢复 → 汇总结果。加入一次进程重启，验证不会丢任务或重复执行已完成步骤。MCP 客户端真实调用保存计划与查询结果工具。该闭环是基础验收，不能替代最终真实 Claude/Codex 验收。

## 规格必须解决的歧义

- 连续失败三次究竟进入不稳定还是离线，明确计数是否重置。
- “恢复后五秒”从哪一个事件计时，与三秒探测及三次成功门槛如何协调。
- 稳定窗口只是估计，置信度与实际 API 成功率分别测量。
- 白名单不等于沙箱；测试命令也可能写文件或联网。
- 非幂等命令中断后的恢复策略与回滚失败的报告方式。
