# 云驿（yunyi） 路线图

## 概览

为本地 Coding Harness 提供网络状态感知、预先规划的离线任务执行、检查点与恢复。用户于 2026-09-26 确认多规格拆分路线，要求先串行 spike，再完整 SDD，规格通过后进入 kiro-impl，严格 agentic-tdd，最小闭环通过前不得开启高并发。

## 方案决策

- 选择：按状态账本、安全执行、Harness/MCP 集成拆为三份规格；先冻结接口，再实现纵向闭环。
- 原因：共享持久化和动作权限是下游前提，不能让多个实现代理各自猜测。
- 未选择：单一大规格会弱化责任边界；先全功能透明代理受客户端网络行为制约过大。
- 当前状态：基础依赖、Claude/Codex受限联机spike及TDD工具链三项独立审查已通过。产品最小闭环尚未实现，规格内容待审阅。

## 范围

- 包含：CLI 七类命令、daemon、四态网络状态机、SQLite、八项 MCP 工具、结构化规划、安全串行离线执行、恢复与受管回滚、Claude/Codex 适配、测试、中文文档与开源许可证。
- 排除：修改 Harness 源码、网络透明中间人、云端请求撤回、任意程序副作用的事务回滚、离线调用云模型、多用户服务。
- 需要审阅的现实边界：本地暂停仅尽力；未确认独占工作区时不自动离线写入；未知执行结果不重放；真实 Harness/云规划验收保持独立发布门禁。

## 约束

- 全部 Python 使用 conda 解释器；本项目固定 pack311（Python 3.11.14）。不调用系统 Python。
- 一条实现流水线同时只执行一个任务；测试作者、代码作者、三个审查者使用隔离上下文。
- 产品代码不得从 .spikes 直接复制；spike 只提供依赖证据和技术决策。
- 不读取、打印或新增云端密钥。规划默认借助既有 Harness 会话；真实调用若需要用户凭据或付费配额，再走明确的运行验收。
- 所有生成文件须区分“技术审查通过”与“用户批准”；未批准的 tasks 不进入实现。

## 边界策略

基础规格唯一拥有通用配置、状态、计划数据契约与数据库；执行规格唯一拥有动作权限、执行、快照和恢复政策；集成规格唯一拥有 CLI、daemon、MCP、Harness 和规划编排。
上游协议或 schema 变化必须重新验证下游；禁止下游直接修改数据库 schema。

## Specs (dependency order)

- [ ] yunyi-foundation — 配置、网络观测、持久化、模型与日志。Dependencies: none
- [ ] yunyi-execution — 安全动作、离线调度、检查点、精确回滚与恢复。Dependencies: yunyi-foundation
- [ ] yunyi-integration — CLI、daemon、MCP、Harness、规划及端到端集成。Dependencies: yunyi-foundation, yunyi-execution

## 验收与并发顺序

1. 串行验证工具链：依赖导入、MCP 握手、真实 RED/GREEN、反作弊及独立审查。
2. 完整规格包及所有依赖 spike 通过，用户确认具体行为边界。
3. 串行实现最小纵向闭环：预置计划 → fake harness/探针 → 断网 → 一步执行 → 检查点 → 恢复报告 → 重启验证。
4. 只有该闭环通过后，才可对无共享文件、无未完成依赖的任务使用并行；同时最多两个实现单元，集成与提交仍串行。用户所说高并发作为后续优化，不能默认开启四路开发。
5. 完整模拟轨迹、真实 Harness MCP 连接、真实规划及恢复计时完成后，才宣称完整产品验收。
